# Strait vs 其他方案

[English](../en/comparison.md) | 中文

> 以下对比基于公开文档和主流使用场景。每个工具各有优势，Strait 聚焦于管线可编程性和插件深度。

## 对比表

| 能力 | LiteLLM | Kong AI Gateway | Strait |
|------|---------|-----------------|--------|
| 定位 | 多供应商代理 | API 治理 + AI 扩展 | 可编程 AI 请求管线 |
| 多供应商路由 | 极强（100+ 供应商） | 强大 + 语义路由 | 模型级 YAML 路由 + 插件化 |
| 请求拦截 | Hooks 回调 | 通用插件 | 原生六阶段管线 |
| 流式响应后处理 | post_call 较重 | 通用转换器 | 原生 StreamPostProcessor |
| 深度请求/响应处理 | Pre/Post hooks | AI Request/Response Transformer | 预处理 + 后处理独立阶段 |
| 插件机制 | Python hooks + 回调 | Lua 插件系统 | Go 原生接口（类型安全） |
| 插件热重载 | 配置重载 | 成熟支持 | 原子指针替换，零中断 |
| 插件自描述 | 无 | 部分（插件配置） | 自动生成 manifest.json |

## Strait 独特能力

- **请求深拷贝隔离** — 管线入口对请求做深拷贝，预处理器的修改不会影响原始 payload
- **插件失败策略** — 严格（中断）、跳过（忽略并继续）、降级（使用默认值）——由调度器处理，不需要插件自己实现
- **TraceID 全链路追踪** — 每个请求分配唯一标识，贯穿六个阶段，日志中可通过 `trace_id` 关联
- **插件自描述** — 插件通过 `Descriptor()` 声明类型、优先级、失败策略和配置 Schema，启动时自动生成 manifest

## 什么时候选 Strait？

- 你需要对 AI 请求的**全生命周期**做深度控制（不只是路由转发）
- 你想用 Go 写插件逻辑，而不是 Python hooks 或 Lua 脚本
- 你需要流式响应的后处理能力（审计、token 统计、内容过滤）
- 你需要插件级别的失败隔离和降级策略

## 什么时候不选 Strait？

- 你只需要简单的多供应商路由 → LiteLLM 更合适
- 你需要企业级 API 网关（限流、配额、开发者门户）→ Kong 更成熟
- 你不需要自定义插件逻辑 → 直接用 OpenAI SDK + 环境变量切换供应商
